# v0.2.0 performance principles

Learning note. Context: v0.1.0 shipped a complete single-table engine; v0.2.0 is the
"fast" phase. This note records the principles agreed for that phase, the concrete
improvements planned per area (load, processing, write), and the central concept that
decides *where* parallelism pays off: CPU-bound vs memory-bound work. It seeds the
v0.2.0 roadmap entry in [README.md](README.md) and the task view in
[todo.md](../todo.md).

## The central concept: CPU-bound vs memory-bound

Goroutines are green threads managed by the Go runtime: starting one costs ~2KB of
stack (vs ~1MB for an OS thread), and the scheduler multiplexes them over the physical
cores (`GOMAXPROCS`). They are cheap enough that the idiomatic pattern is one goroutine
per unit of work, coordinated with `sync.WaitGroup` or channels.

But the right question is not "should we use goroutines?" — it is **"what limits each
phase: CPU or memory bandwidth?"**

- **Parsing (load) is CPU-bound.** Every input byte triggers real CPU work: tokenizing,
  `ParseFloat`, validation, null rules. Eight cores parsing eight chunks ≈ 8x faster.
  This is exactly how polars reaches 0.032s on the CSV that takes us 0.54s — see
  [Lessons from the first benchmark](first-benchmark-lessons.md).
- **Columnar kernels (processing) are memory-bound.** A `Sum` over a contiguous
  `[]float64` already runs at the speed of the memory bus; the CPU spends most of its
  time *waiting* for data from RAM. Eight goroutines fighting over the same bus gain
  little — there is some headroom, but it is modest and it has a hard ceiling.

Conclusion: **parallelism goes where the benchmark pointed — the loaders.** In the
kernels, the big wins are of a different nature: better algorithms and fewer
allocations, not more goroutines.

## The principles

1. **Measure before touching.** `pprof` first; `go test -bench` + `benchstat` as
   performance regression tests. No optimization lands without a before/after number.
2. **Fast sequential before parallel.** Parallelizing code that over-allocates only
   scales the waste. Clean up allocations first, then split the work.
3. **Parallelism at the boundaries (load/write), not in the kernels.** The CPU-bound
   vs memory-bound distinction above, applied as a rule.
4. **Semantics do not change.** The round-trip tests and the `Example` tests are the
   contract; an optimization that changes results is not an optimization. One
   documented exception: pairwise summation *improves* `Sum`'s accuracy — it explains
   the benchmark's checksum mismatch, and the more accurate answer wins.
5. **No dependencies.** Stdlib only, as everywhere else in grizzly.
6. **The public API does not move.** v0.2.0 is internal; at most new options, never
   breaking changes.

## Planned improvements per area

An honesty note first: **the benchmark only measured load.** For processing and
writing there is no telemetry yet, so in those areas the first step is not optimizing
— it is measuring (principle 1).

| Area | What | Why |
|------|------|-----|
| Load: JSON | `pprof` the current path (the remaining `Decode` calls) | The measured weak point: 3.46s vs polars' 0.75s |
| Load: CSV | Parallel chunk parsing: split the file into byte ranges aligned to `\n`, one goroutine + its own `columnBuilder`s per chunk, concatenate at the end | The polars model; sequential CSV already beats pandas — this attacks the remaining 17x |
| Processing | First: benchmarks for `Filter`/`GroupBy`/`Sort`. Then: pairwise summation in `Sum`/`Avg` | No data yet; pairwise is a safe accuracy win and, being tree-shaped, parallelizes naturally if ever needed |
| Write | First: benchmark. Clear candidate: `strconv.AppendFloat` into reused buffers instead of `fmt` | Formatting floats through `fmt` allocates on every call |

## New Go vocabulary this phase forces

- **goroutines and the scheduler** — green threads, `GOMAXPROCS`, work stealing
- **`sync.WaitGroup`** — "wait until these N goroutines finish"
- **channels** — typed pipes between goroutines; Go's "share memory by communicating"
- **`pprof`** — CPU and allocation profiles, flame graphs
- **escape analysis, applied** — `go build -gcflags=-m` to see what escapes to the heap
- **`benchstat`** — statistical comparison of benchmark runs (is -5% real or noise?)

## The simple version

We tuned our homemade car and the telemetry already told us which track we lose on
(JSON loading). The plan for this season: never touch the engine without putting it on
the dyno first (measure), don't bolt on a second engine while the first one leaks oil
(sequential before parallel), and know which parts of the race are won by engine power
and which by the width of the road — adding horsepower doesn't help where the road is
the bottleneck (CPU-bound vs memory-bound). And whatever we tune, the car must finish
the race with exactly the same passengers (semantics don't change).

## Further reading

- [Concurrency is not parallelism](https://go.dev/blog/waza-talk) — the Go blog post
  around Rob Pike's classic talk: concurrency is *dealing with* many things at once,
  parallelism is *doing* many things at once. The conceptual base for principle 3.
- [benchstat](https://pkg.go.dev/golang.org/x/perf/cmd/benchstat) — the tool that
  turns benchmark output into statistics (median, confidence intervals, p-values);
  the difference between "looks faster" and "is faster". The workhorse of principle 1.
