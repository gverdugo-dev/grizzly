# 08 — I/O: CSV & Parquet

> Status: 🟡 Open for discussion
> Affects: usability, real-world testing, the benchmark story

## The question

How do we get data in and out? CSV first; what about Parquet? And how much do we build by
hand vs use the standard library / existing packages?

## Why it matters

A DataFrame you can't load a file into is a toy. I/O is also where idiomatic Go error
handling, the `io` interfaces, and streaming all show up — great learning surface. And
without realistic files we can't benchmark honestly against pandas/Polars.

## CSV (v1)

Go's standard `encoding/csv` handles the parsing grammar (quoting, embedded newlines) — no
reason to rewrite that. **Our** work is the interesting part:

- **Type inference** — scan values and decide `int64` / `float64` / `bool` / `string` per
  column. (Or accept an explicit schema.)
- **Columnar construction** — append into per-column typed slices as we read.
- **Null detection** — empty fields, configurable NA tokens (`""`, `NA`, `null`).
- **Streaming** — read row-by-row via `csv.Reader`, don't slurp the whole file into memory.

```go
df, err := grizzly.ReadCSV("data.csv", grizzly.WithHeader(true))
```

## Parquet (later ⚪)

Parquet is columnar and the natural format for a columnar DataFrame, but the format is
complex (encodings, compression, metadata). Writing a Parquet reader by hand is a project
in itself — **out of scope for v1**. When we want it, lean on an existing package rather
than hand-rolling.

## Open questions

- [ ] Type inference policy: sample first N rows, or scan the whole column? How do we handle a column that's `int` until row 10,000 then sees a float?
- [ ] Parallel CSV parsing (see [07](07-concurrency.md)) — worth it, given quoted newlines make naive chunk-splitting unsafe? Probably a later optimization.
- [ ] Do we expose a generic `io.Reader` API (not just file paths) from day one? (Idiomatic Go says yes.)
- [ ] Error strategy: fail fast on a bad row, or collect errors and continue?
